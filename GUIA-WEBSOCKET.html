WebSocket no Laravel, passo a passo

Um mapa para entender como uma jogada feita em uma aba aparece na outra, com os arquivos exatos deste projeto.

A ideia Conexão Uma jogada Segurança Reconexão Mapa dos arquivos

1. A ideia em uma frase

HTTP serve para pedir algo e receber uma resposta. WebSocket mantém uma conexão aberta para o servidor enviar novidades ao navegador assim que elas acontecerem.

No Laravel, broadcasting publica eventos em canais. O Reverb mantém as conexões WebSocket. No navegador, Laravel Echo oferece a API para assinar canais e ouvir eventos; pusher-js fala o protocolo usado pelo Reverb.

Neste jogo: o navegador envia ações, como desenhar e palpitar, por HTTP. O WebSocket entrega as atualizações do servidor às abas conectadas. O Reverb não substitui as rotas da API.

2. Como uma aba começa a escutar

ReactAbre conexão com Reverb na porta 8080.
EchoPede o canal privado participants.ID.
Laravel HTTPAutoriza a inscrição usando o token Bearer.
ReverbEntrega eventos desse canal à aba autorizada.
  1. Conectar: em resources/js/app.tsx, um useEffect cria Echo com broadcaster: 'reverb'. Os valores VITE_REVERB_* dizem ao navegador onde está o servidor WebSocket.
  2. Pedir inscrição: echo.private(`participants.${state.you.id}`) solicita o canal do participante atual. O canal privado precisa de autorização; conhecer seu nome não basta.
  3. Autorizar por HTTP: Echo envia POST /api/broadcasting/auth com o token Bearer. AppServiceProvider.php registra essa rota com auth:participant. A regra em routes/channels.php só permite participants.ID quando o ID é o do participante autenticado.
  4. Ouvir: depois da inscrição, .listen('.game.updated', ...) recebe o conteúdo do evento e chama acceptRef.current(event). O ponto inicial em .game.updated indica o nome personalizado definido por broadcastAs().
// resources/js/app.tsx — versão reduzida
echo.private(`participants.${state.you.id}`)
  .listen('.game.updated', (event) => acceptRef.current(event));

A porta 8000 atende a página e a API Laravel; a porta 8080 atende o Reverb na configuração local de exemplo. composer run dev inicia ambos, além do agendador e do Vite.

3. Acompanhe um traço desenhado

  1. Entrada: DrawingCanvas.tsx captura pontos do ponteiro. GameScreen.tsx passa o lote para enqueue em app.tsx.
  2. Envio: drain envia POST /api/room/draw. O traço já aparece localmente enquanto aguarda a confirmação.
  3. Servidor: GameController.php valida os dados; Game.php verifica papel, rodada e revisão, e grava a alteração no banco.
  4. Publicação: Game.php::notify() prepara um evento para cada participante. DB::afterCommit espera a transação terminar, então dispara GameUpdated. Esse evento usa ShouldBroadcastNow para transmitir imediatamente, sem um worker de filas.
  5. Entrega: GameUpdated.php publica em PrivateChannel('participants.ID'). O driver Reverb entrega game.updated às abas inscritas.
  6. Tela: o listener no app.tsx chama accept. Ele combina a atualização com o estado atual e o React redesenha os componentes.
// Ideia do conteúdo de um evento; campos ilustrativos
{
  "state": { "round_number": 1, "version": 8, "revision": 3 },
  "delta": { "kind": "stroke", "chunk": { "points": [[10, 20]] }, "revision": 3 },
  "guess_update": null
}

O desenho é transmitido como pontos, cor e espessura; não como uma imagem inteira. Para palpites, o mesmo evento pode incluir guess_update em vez de um delta de desenho.

4. Por que o canal é por participante?

RoomState.php monta uma versão do estado para cada pessoa. Durante a rodada, o avaliador pode receber o objeto secreto e a proximidade numérica; o desenhista não recebe esses campos. Por isso Game.php::notify() percorre os participantes e cria um conteúdo próprio para cada canal.

A autenticação por Bearer identifica o participante; routes/channels.php impede que ele assine o canal de outra pessoa. A chave pública REVERB_APP_KEY identifica a aplicação no Reverb. Ela não substitui o token do participante e não dá acesso a canais privados. REVERB_APP_SECRET permanece no backend.

5. E se o WebSocket falhar ou chegar fora de ordem?

O estado verdadeiro fica no servidor. O app.tsx também consulta GET /api/room ao entrar, ao reconectar, quando a aba volta a ficar visível e a cada cinco segundos. Assim, a tela se recupera de eventos perdidos. Uma falha no envio do broadcast é registrada no Laravel, mas não desfaz a jogada já confirmada no banco.

roundUpdates.ts compara rodada, versão e horário para rejeitar atualizações antigas. No desenho, a revisão permite detectar uma lacuna; quando isso acontece, o cliente busca o desenho completo por HTTP.

Regra para lembrar: WebSocket acelera a atualização da interface; HTTP recupera o estado completo e envia as ações. O banco guarda o resultado permanente.

Como observar em execução

Com composer run dev ativo, abra duas abas do jogo. Nas ferramentas de desenvolvimento do navegador, veja a requisição /api/broadcasting/auth na aba Network e a conexão WebSocket na seção WS. Para acompanhar mensagens no terminal, inicie o Reverb com php artisan reverb:start --debug em vez do comando padrão.
